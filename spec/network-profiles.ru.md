## 0. Цель

На одной машине одновременно работают несколько нативных агентских сред. Каждый запуск должен выходить в сеть через собственный прокси уровня приложения, не меняя оркестратор, соседних агентов и операционную систему:

```text
codex A  ─► proxy :18081 ─► VPN / upstream A
claude B ─► proxy :18082 ─► VPN / upstream B
pi C     ─► proxy :18081 ─► VPN / upstream A
orchestrator and everything else ─► the machine's ordinary network
```

Запуск сохраняет своё окружение, учётные данные, привязку среды выполнения, модель и рабочий каталог; сетевой профиль меняет только то, как устанавливаются поддерживаемые соединения. Первый релиз — это **кооперативная маршрутизация поддерживаемых клиентов через прокси**, а не принудительная изоляция дерева процессов. Поэтому он называется *сетевыми профилями* и никогда *сетевой песочницей*. Будущая принудительная песочница использует тот же профиль как описание своего выхода в сеть.

## 1. Факты платформы (проверены, если не помечено иное)

| Факт | Где |
| --- | --- |
| Есть три владельца процессов, и каждый запускает процессы агентских сред из значений, которые сам собирает: `curator-run` (интерактивные запуски), `internal/spawn` в task-board (отслеживаемые дочерние агенты), tb-sessiond (основные сессии доски, хост app-server для codex, PTY для claude) | LP §3.3, LP-D5, LP-D6 |
| `curator-run` собирает argv плана → флаги промпта → флаги MCP → нативный хвост и применяет четыре слоя окружения; его отслеживаемый транспорт несёт только собственные литералы, `env_names`, `argv_suffix` и stdin | README лаунчера, раздел «Environment and transport»; SPEC 0.4.0-draft §4.5–4.6 |
| Плагины модуля фильтруют окружение дочернего процесса: codex удаляет одиннадцать конкретных ключей (`CODEX_*`, указатели на эндпоинты task-board) и чистит `PATH`; claude удаляет только `CLAUDECODE`; pi передаёт окружение родителя как есть | модуль: `internal/runtimeenv`, `systems/claude/env.go`, `systems/pi/env.go` |
| Запрос плана запуска в ax: `env_literals` (значения) и `env_names` (поиск по имени на стороне получателя); имя, которое есть и среди литералов, выбрасывается из списка разрешённых с предупреждением | спецификация ax §14.1; curator-spec Decision 0013 D6.3 |
| Claude Code документирует `HTTP_PROXY`/`HTTPS_PROXY` (и `NO_PROXY`) и не поддерживает SOCKS; фоновых агентов обслуживает общий супервизор на пользователя, который может сохранить окружение первой оболочки, запустившей его | документация Claude Code (для детали про супервизор — docs-confidence) |
| OpenCode документирует переменные прокси и то, что прокси нужно обходить для его локального TUI-сервера | документация opencode (docs-confidence) |
| Websocket-дозвонщик Codex понимает стандартные переменные прокси и маршруты прокси | чтение исходников codex (для установленной сборки — docs-confidence) |
| `curl` читает только `http_proxy` в нижнем регистре; `NO_PROXY=*` отключает прокси; клиенты расходятся в регистре и приоритете | документация curl |
| Локальные движки под `curator-inference-manager` слушают loopback; у direct нет прокси и нечего обходить, поэтому проверка покрытия хостов движков к нему не применяется. Профили движков в режиме SSH подключаются к удалённым машинам по собственному каналу | LP-D7, LP-D8; `model-harness` в agents-infra, `mode = local\|ssh` |

## 2. Решения

### N1 Пять независимых настроек запуска

| Настройка | Что решает | Владелец |
| --- | --- | --- |
| Профиль окружения (Curator) | контекст, домашний каталог, скиллы, MCP, граница учётной записи | Curator |
| Выбор учётных данных | какой вход использует домашний каталог (`shared`/`isolated`) | Curator |
| Привязка среды выполнения (LP-D1) | какая агентская среда к какому провайдеру или движку ходит | конфигурация task-board + каталог модуля |
| **Сетевой профиль** | через какой прокси уровня приложения идут поддерживаемые соединения | `curator-network-profiles` + владелец процесса |
| Профиль исполнения | где и в каких пределах работают инструменты | среда исполнения |

Сетевой модуль никогда не копирует логины, не меняет домашние каталоги провайдеров, не выбирает учётную запись и не сбрасывает учёт квот; другой маршрут никогда не становится новым доменом квоты. Словарь CLI следует форме командной строки от 2026-09-27, которая заменяет словарь LP-D12: `--runtime <id>` (псевдоним `--agent`) для привязки, `--profile <name>` для профиля Curator и в task-board, и в `curator run`, а **`--network <name>`** для сетевого профиля. Слово `profile` без уточнения означает только профиль Curator; сетевой профиль никогда не выбирается через `--profile`.

### N2 Одна библиотека, три владельца процессов

Go-модуль **`curator-network-profiles`** (имя решено 24.09.2026): `resolve → validate → conditional probe → patch` (direct и планы/сухие запуски пропускают все пробы). Он не импортирует ни task-board, ни `curator-model-router`, ни хранилище ax: это его вызывающие. Он не создаёт процессов и не владеет демоном.

Каждый владелец процесса применяет привязку непосредственно перед запуском на каждом своём пути создания процессов: `curator-run` (интерактивные запуски), `internal/spawn` в task-board (дочерние агенты, повторы, рекурсивные запуски рабочих, возобновление), tb-sessiond (основные сессии, включая хост app-server для codex и PTY-хост для claude, при запуске и при возобновлении). `curator-inference-manager` — четвёртый владелец процессов, только его процессы — движки, а не агентские среды: сетевая часть движков вне этого эпика (N12).

### N3 Модель данных

`NetworkSelection` (что попросил вызывающий): `profile_ref`, `origin ∈ {explicit, inherited, runtime-default, project-default, operator-default}`, `required_assurance ∈ {cooperative, enforced}`.

`inherited` означает, что владелец процесса передаёт разрешённую ссылку родителя, сохранённую при резервировании, для повторного разрешения на хосте ребёнка; библиотека никогда не извлекает её из окружения или значений прокси.

`NetworkProfile` (что есть на машине) хранится в файле оператора `~/.curator/network.toml` (на хосте платформы Swarma — каталог и политика привязки, которыми владеет root, вне домашних каталогов агентов, N15): для каждой плоскости — один машинный каталог, рядом с остальными файлами оператора в `~/.curator/`; лаунчер и task-board никогда не держат двух копий. Его предлагали как `$XDG_CONFIG_HOME/curator-network-profiles/network.json`; curator-playbook `spec/process-configuration.md` §2.3 перенёс его; выбран TOML, потому что люди редактируют файл вручную. Имя таблицы `networks` — *предложено*: слово `profile` обозначает только профиль Curator.

```toml
schema = "relux-network-profiles-v1"

[networks.egress-a]
kind         = "external-http-proxy"
endpoint     = "http://127.0.0.1:18081"
bypass_hosts = ["localhost", "127.0.0.1", "::1"]

[networks.egress-b]
kind         = "external-http-proxy"
endpoint     = "http://127.0.0.1:18082"
bypass_hosts = ["localhost", "127.0.0.1", "::1"]
```

Виды профилей: `external-http-proxy` и `direct`; хост платформы Swarma не привязывает ни один из них и вместо них обслуживает профили `platform-proxy` (*предложено*, N15, пункты 2 и 5). Именованный профиль `kind = "direct"` не содержит `endpoint`, `bypass_hosts` или `probe_target`; эти ключи ОБЯЗАНЫ отклоняться при наличии, даже если они пусты.

```toml
[networks.direct]
kind = "direct"
```

Файл редактируют через `curator network add|remove` или вручную. Добавление или изменение любого сетевого профиля, включая direct, — запись, расширяющая разрешения, потому что оно меняет маршрут трафика: оно вступает в силу только после `curator network confirm`, а эта команда отказывается выполняться в агентской сессии (relux-works/curator-trust `spec/trust.md` §10).

`NetworkBinding` (что применяется): `profile_ref`, `profile_digest`, `adapter_identity` (сборка агентской среды + точка входа + плагин), `resolved_endpoint`, `assurance`, `env_patch`; позже `lease_id` и `generation` для управляемого шлюза. Манифесты запусков хранят `profile_ref`, `profile_digest`, `adapter_identity`, `assurance` и результат пробы; полное окружение и адрес с учётными данными туда никогда не попадают. Дайджест фиксирует конфигурацию, а не фактический выход внешнего прокси в сеть.

`env_patch` — это две упорядоченные операции, сначала `unset`, потом `set`. `unset` удаляет из окружения хоста, который создаёт процесс, все известные адаптеру переменные семейства прокси в обоих написаниях, а `set` записывает согласованный набор прокси из N5 (пустой для direct); патч никогда не состоит из одних добавлений. `profile_digest` считается по нормализованному итоговому профилю (версия схемы, вид, эндпоинт, отсортированные `bypass_hosts`, *режим* учётных данных без секретов; для direct — только версия схемы, вид и режим учётных данных) и никогда по результатам проб, идентификаторам аренд или временным меткам. Две привязки **равны**, когда равны `profile_digest`, `adapter_identity` и `assurance`; совпадение имени профиля ничего не доказывает.

Запись в `runtimes.toml` (LP-D2) МОЖЕТ нести `network = "<name>"` как значение по умолчанию для этой привязки, а конфигурация проекта МОЖЕТ нести `spawn.network.default = "<name>"` (решено 2026-09-22 после ревью). Оба значения — стабильные идентификаторы профилей: их разрешают на каждой машине, а там, где такого профиля нет, следует отказ `network_profile_unknown`. Явный `--network` важнее обоих.

### N4 Приоритет и уровень гарантии

На хосте платформы Swarma выбирает машинная привязка из N15, а всё ниже только сверяется с ней. В остальных случаях: блокировки хоста и набор разрешённых профилей → явный выбор → унаследованный выбор → значение по умолчанию привязки среды выполнения → значение по умолчанию проекта → значение по умолчанию оператора (собственная запись машины со значением по умолчанию в `network.toml`). Если не выбрано ничего, поведение остаётся сегодняшним и сообщается как `unmanaged`, а не как «прямое». Явный выбор именованного direct — управляемый запуск: он проходит проверку набора разрешённых профилей и подтверждения, а в запись попадают его `profile_ref` и дайджест. Запрос `enforced` на машине, где есть только кооперативный бэкенд, отклоняется; первый релиз публикует `assurance = cooperative`.

### N5 Применение патча без побочных эффектов

Патч попадает только в приватное окружение дочернего процесса. Никогда не `os.Setenv`, не профили оболочки, не системный прокси, не общее окружение tmux и не переписывание пользовательского `settings.json`. Порядок: убрать все конфликтующие унаследованные переменные прокси, затем выставить согласованный набор:

```text
HTTP_PROXY=<endpoint>   HTTPS_PROXY=<endpoint>
http_proxy=<endpoint>   https_proxy=<endpoint>
NO_PROXY=<bypass list>  no_proxy=<bypass list>
```

Для `direct` патч содержит **только unset**: то же семейство прокси удаляется без учёта регистра, а set пуст. Ребёнок direct не видит унаследованных переменных прокси; unmanaged сохраняет текущее окружение.

`ALL_PROXY`, переменные для websocket и настройки среды выполнения добавляет только адаптер агентской среды в модуле, и только после проверки; никто не выставляет десяток переменных на веру. Если нативные настройки инструмента перекрывают окружение, адаптер применяет поддерживаемое переопределение на один запуск или отказывает с `network_configuration_conflict`; общую конфигурацию он никогда не переписывает. Переменные прокси — это **собственные литералы** владельца процесса, ровно как `ANTHROPIC_BASE_URL` в транспорте `env-bundle` для claude (LP-D3); в документе ax они едут как `env_literals`, никогда как `env_names`. Собственная подготовка Curator (`curator env resolve`, установка, починка) по умолчанию через прокси не идёт; проксирование подготовки — отдельное явное требование.

### N6 Форма шлюза

Общая поверхность — **HTTP-прокси с CONNECT**, потому что Claude Code поддерживает переменные HTTP/HTTPS-прокси и не поддерживает SOCKS. За ней может стоять вышестоящий HTTP-прокси, SOCKS или конечная точка WireGuard. Первый кандидат на управляемый бэкенд — sing-box со слушателем `mixed` на loopback, `set_system_proxy: false`, без TUN, с WireGuard без системного интерфейса и закреплённой поддерживаемой версией. На этапе A шлюз настраивает оператор: библиотека только читает профиль и проверяет эндпоинты прокси пробой (для direct пробы пропускаются), а запускает владелец процесса или `curator network exec`. Это сетевой туннель, а не LLM-шлюз: API моделей, промпты, идентификаторы моделей и учётные данные не трогаются; проверка TLS остаётся включённой; корпоративная инспекция TLS — отдельный явный режим.

### N7 Поддержка агентских сред зависит от формы запуска

Поддержка проверяется для кортежа `harness build + entrypoint + adapter + configuration profile`, а не для «claude вообще». MVP поддерживает **свежий процесс агентской среды на каждый запуск**. Подключиться к уже работающему app-server или демону можно, только если его привязка равна запрошенной или адаптер умеет задать маршрут на уровне сессии; иначе `network_scope_unsupported`. Claude `--bg` через общий супервизор явно не поддерживается. tb-sessiond проверяет равенство привязок своих хостов при запуске и при возобновлении. Различаются два события: **новое назначение** на уже работающий хост и **повторное подключение или возобновление** существующего запуска. Переходы зафиксированы:

| Событие | Ситуация | Итог |
| --- | --- | --- |
| новый запуск | свежий процесс | разрешить, привязать, запустить |
| новое назначение на работающий хост | привязка хоста равна (N3) разрешённой | подключиться |
| новое назначение на работающий хост | привязка отличается, адаптер умеет маршрут на уровне сессии | задать маршрут для сессии, записать привязку |
| новое назначение на работающий хост | привязка отличается, маршрута на уровне сессии нет | отказ `network_scope_unsupported` |
| повторное подключение или возобновление существующего запуска | записанная привязка равна свежему разрешению | подключиться заново / возобновить |
| повторное подключение или возобновление существующего запуска | то же имя профиля, другой дайджест | отказ `network_profile_drift`; перемаршрутизация на уровне сессии не обходной путь; оператор восстанавливает профиль или начинает новый запуск |
| повторное подключение или возобновление существующего запуска | профиль отсутствует или запрещён | `network_profile_unknown` / `network_profile_denied` |

Операции «сменить сетевой профиль» на уровне сессии в MVP нет; она появится вместе с поколениями шлюза (N14). Новые пути агентских сред попадают в матрицу по мере появления: exec-режим `pi-native` (LP-D8) и плагин opencode (LP-D3); матрица перепрогоняется на каждом закреплённом релизе инструмента.

### N8 Точки интеграции

- `curator run <runtime> --profile <p> --network egress-a -- <args>`: разрешить, проверить совместимость, сделать ограниченную по времени предварительную проверку только для профилей прокси, наложить патч после обычной сборки окружения; допуск и поздние проверки не меняются.
- `task-board spawn … --network egress-a`, а также `spawn.network.default` и `network` у привязки: оркестратор выбирает идентификатор профиля из разрешённого набора и никогда не передаёт сырой адрес прокси. Дочерний агент наследует профиль **по ссылке с повторным разрешением**, с `origin = inherited`, а не копированием окружения оркестратора; родитель на A может запустить ребёнка на B.
- Манифесты: рядом с `RuntimeProvenance` и `profile.name`/`lock_sha256` из Curator (LP-D11) — `network.profile_ref`, `profile_digest`, `adapter_identity`, `assurance`.

### N9 Отслеживаемые сессии (ax)

Отслеживаемый транспорт сериализует только собственные литералы, поэтому прокси, выставленного на самом внешнем процессе, недостаточно для надёжного возобновления. Ссылка на сеть и дайджест едут в версионированном контракте. Фактический хост процесса разрешает привязку непосредственно перед запуском или возобновлением и заново собирает из неё окружение дочернего процесса. Половина `unset` патча выполняется против собственного унаследованного окружения хоста, так что конфликтующая переменная, которая есть только на хосте, удаляется там; литералы, которые несёт транспорт, — это только половина `set`. Пока этого нет, отслеживаемый режим с обязательным сетевым профилем отказывает; прямой режим выходит независимо.

### N10 Жизненный цикл, проверки, ошибки

`resolve → validate profile + adapter → conditional bounded proxy preflight → prepare binding → spawn → record outcome`. Direct и планы/сухие запуски пропускают предварительную проверку; их поля tcp/connect/tls в `ProbeRecord` равны `skipped`. На этапе A нет ни планировщика, ни регистрации демона, ни модели аренд. `curator network show` и план только читают; `curator network check` проверяет без сетевого вызова, а `check --probe` для профилей прокси — явный сетевой вызов (предложенный `netrun doctor`); предварительная проверка запуска ограничена по времени и не использует учётные данные моделей. Три разных факта: открытый TCP-порт; успешный CONNECT и TLS до согласованной цели; внешний IP, увиденный только для этой проверки. Коды сбоев: `network_profile_unknown`, `network_profile_denied`, `network_scope_unsupported`, `network_configuration_conflict`, `network_proxy_unreachable`, `network_proxy_auth_failed`, `network_profile_drift`. Если профиль отсутствует, запрещён, не поддерживается или недоступен, агент не запускается: скрытого перехода на прямое соединение нет, автоматического переключения VPN или учётной записи тоже; отказ запуститься — это не аварийный выключатель ОС. О разрыве посреди запуска сообщается владельцу запуска, и решает он; ничто не перезапускает задачу безусловно.

Для direct предварительная проверка и `check --probe` пропускают все три шага (`tcp`, `connect`, `tls` = `skipped`); подключений к эндпоинту нет.

### N11 Граница покрытия и секреты

Direct тоже кооперативный: удаление переменных прокси не гарантирует прямой маршрут на уровне ОС.

Профиль действует на поддерживаемые сетевые клиенты агентской среды, а это может быть не только инференс, но и обновление авторизации, HTTP MCP и другие запросы. Дочерние команды могут унаследовать переменные, но подчиняются ли они им, зависит от клиента, а не гарантируется ОС. Вспомогательный процесс, который запускает агентская среда (stdio MCP-сервер, мост инструментов), наследует патч, как любой дочерний процесс. Если такому процессу нужно ходить к управляющей плоскости своим маршрутом, его исходящий клиент настраивается явно и никогда не берётся из унаследованных переменных прокси. Так выход агентской среды в сеть и транспорт моста проверяются вместе, а упавший прокси инференса никогда не роняет управляющий канал. Вне гарантии: отдельно открытый браузер для OAuth, уже работающие сервисы, сырые сокеты и UDP, инструменты, выполняемые на удалённом EnvironmentHost. Пароли вышестоящих прокси и ключи WireGuard живут в шлюзе; агент получает эндпоинт на loopback. Слушатель на loopback без аутентификации клиента не изолирует локальные процессы друг от друга. В логи пишутся запуск и попытка, идентификатор профиля, дайджест, адаптер и сборка, результат пробы; сырое окружение, токены, `Authorization`, `Proxy-Authorization` и тела запросов не пишутся никогда.

### N12 Движки

Локальные эндпоинты `curator-inference-manager` находятся на loopback и ОБЯЗАНЫ стоять в `bypass_hosts` каждого прокси-профиля, иначе агентская среда пойдёт к своей локальной модели через прокси. У direct нет прокси, поэтому нечего обходить и проверка покрытия хостов движков не применяется. Профили движков в режиме SSH подключаются через собственный канал провайдера движков, и переменные прокси агентской среды их не касаются. Будущая принудительная песочница считает движок на loopback локальным сервисом, который нужно разрешить явно, а не «интернетом».

### N13 Роутинг

`curator-model-router` решает, что запускать; `curator-network-profiles` решает, через какой разрешённый маршрут это подключается. Роутер может учитывать совместимость с обязательным сетевым профилем как ограничение и никогда не переключает VPN, учётные данные или домены квот. Привязка среды выполнения, у которой в каталоге по умолчанию стоит другой профиль, — это не переключение маршрута роутером. До подсчёта оценок `CandidateResolver` вызывающего разрешает зависимые настройки каждого кандидата (сетевой профиль, профиль Curator, домашний каталог) по приоритету N4. Явно запрошенный профиль он фиксирует для всех кандидатов и исключает кандидата, у которого разрешённое значение отличается от зафиксированного, если только маска свободных полей политики роутинга не освобождает этот член (спецификация роутинга, R7). Это разрешение — поиск по данным, а не проба прокси; предварительная проверка N10 остаётся отдельным шагом запуска. Сбой сети — не свидетельство о качестве модели и никогда не снижает её оценку в кодинге. У бэкенда-оценщика свои явно назначенные учётные данные, выход в сеть и политика данных.

### N14 Будущее: управляемый шлюз

Добавляет `acquire / inspect / release`. Аренда принадлежит владельцу фактической среды выполнения, а не короткоживущему лаунчеру, который передал сессию дальше; завершение одного агента не должно останавливать прокси для остальных; изменение конфигурации создаёт новое поколение шлюза и никогда молча не переносит активные сессии. Принудительная песочница исполнения — отдельный эпик, и она использует профиль как описание своего выхода в сеть.

### N15 Хосты платформы: машинная привязка и служебные учётки (Swarma v1)

Действует на хосте, где платформа Swarma запускает каждого агента под своей учёткой ОС, а файрвол по UID в менеджере пользователей v1 делает сетевые профили **принудительными**. Принято оператором 12.10.2026 по итогам ревью архитектуры платформы (находки F-27 и F-24 в `relux-works/swarma-architecture-review`, FINDINGS.md). Пересмотрено 13.10.2026 по решению оператора о доступе в интернет:
- внутри платформы учётке агента закрыт интернет, кроме того, что нужно его собственному агентскому циклу;
- доступ к вебу по умолчанию выключен: задача несёт нужные ей ресурсы, а поиск можно включить только для личностей доверенного круга (пункт 12);
- агенты не собирают и не тестируют, поэтому зависимости скачиваются только на внешних проверочных раннерах (N16).

N15 пересматривает N3, N4 и вектор S7 **для таких хостов**; машина оператора без платформы живёт по N3 и N4 как написано. Пункты 1–9 были черновыми решениями линии, а не решениями владельцев D-*. Пункты 10–12 и изменения 13.10 в пунктах 2 и 5–9 применяют решение оператора. Здесь же применены находки цикла ревью 3, принятые оператором 13.10.2026: в пункте 11 — перечень защиты адресов (F-34), непрерывность суточного объёма (F-68) и то, что гарантирует `CONNECT` (F-33), с согласованными формулировками в пункте 12 и в пункте 3 N16.

1. **Владение.** Каталог и **политика привязки** лежат в месте, которым владеет root и которое агенты могут только читать; пишут туда только установщик платформы или оператор, рядом с конфигурацией менеджера пользователей, и никогда не в домашнем каталоге агента. Собственный `~/.curator/network.toml` учётки агента при выборе не читается: при учётке на агента этот файл может переписать тот самый оркестратор, чьих детей он должен ограничивать, так что набор разрешённых профилей там выдан самому себе.
2. **Привязка.** Связывает допущенную идентичность профиля Curator — имя **и** отпечаток lock-файла (`lock_sha256`, LP-D11), никогда одно имя — ровно с одной ссылкой на сетевой профиль и его `profile_digest`. На хосте платформы привязка никогда не называет профиль `direct` или `external-http-proxy` — ни для какого класса учёток. `direct` ничем не ограничен, а внешний прокси оператора не может опубликовать доказательство обслуживаемой политики из пункта 5. Оба вида остаются для машин оператора без платформы (N3, N4). Профили в грантах уже сужаются по цепочке делегирования, поэтому вместе с ними сужается и выход в сеть. Один профиль Curator — один выход; отдельное сетевое измерение гранта добавляется, только если профилю когда-нибудь понадобится несколько выходов. CIP-0011 §6 ссылался на таблицу `[bindings.profiles]` в `~/.curator/network.toml`; в этой спецификации такой таблицы нет, и эта привязка заменяет тот путь.
3. **Приоритет на хосте платформы.** Выбирает привязка, больше ничего. Явный `--network`, унаследованная ссылка и значения по умолчанию среды выполнения, проекта и оператора только сверяются с ней и при расхождении отклоняются с `network_profile_denied`. Вектор S7 («явный direct перекрывает профиль родителя в пределах разрешённого набора») на хосте платформы не действует.
4. **Закрепление при допуске.** Диспетчер платформы разрешает привязку, когда допускает запуск, и закрепляет ссылку и отпечаток в записи запроса. Повторы и восстановление применяют ту же пару; изменение привязки или каталога до применения файрвола приводит к отказу, а не к другому профилю. Это форма `network_profile_drift` (N7) для платформы.
5. **Что обслуживает слушатель.** На хосте платформы прокси выхода — доверенная служба под собственной служебной учёткой, с **отдельным слушателем на каждое привязанное поколение учётки**. Слушатель TCP на loopback не может определить, какая учётка подключилась, а квотам и журналу по личности (пункт 11) эта атрибуция нужна; поэтому строка файрвола учётки пропускает только порт её собственного слушателя. Вид профиля (`platform-proxy`, *предложено*) несёт обслуживаемую политику из пункта 11: разрешённые записи, квоты и версию защиты адресов. Отпечаток покрывает всё это. Прокси публикует для каждого слушателя `{listener, account_generation, profile_ref, service_generation, served_policy_digest}`. Применение файрвола отклоняется, если обслуживаемый отпечаток слушателя не равен привязанному для профиля; тогда запись о применённом состоянии удостоверяет обслуживаемую политику, а не метку. Каноническое соотношение `profile_digest` и отпечатка обслуживаемой политики задаётся в приложении с контрактом до включения; равными они не считаются. Привязка держится за слушатель и поколение его службы на всё время жизни слушателя; перезагрузка или повторно занятый порт никогда не меняют выход уже привязанных агентов.
6. **Сужение доходит до работающих агентов.** Суженная привязка или обслуживаемая политика применяются к существующим размещениям журналируемым переприменением: на стороне ядра сбрасываются состояния учётки (менеджер пользователей §8), а прокси обрывает или перепроверяет сессии, открытые по старой политике. Без этого бессрочный агент сохраняет старый, возможно более широкий выход.
7. **Служебные учётки платформы (F-24).** У диспетчера и хоста сессий профиля нет: их строка по UID запрещает весь выход. Брокер учётных данных получает свой профиль и слушатель (`swarma-broker-vendor`, *предложено*); его список — множество адресов входа и обновления токена вендора, **как его наблюдают** проверочные строки R8 и R9 ([проверка агентских сред](../docs/harness-verification.md#planned-rows-for-the-platform-broker)), и никогда не копия списка `credential_binding` брокера. Пока эти строки не пройдены для точной сборки Codex, профиль брокера не пишется. Наблюдение для `codex-cli` 0.159.0 от 12.10.2026: вход по коду устройства, обмен кода на токены, обновление и выход ходят только на `auth.openai.com:443`; обновление нужно вызывать без хода агента, потому что `codex exec` добавляет `chatgpt.com`, `ab.chatgpt.com` и `*.oaiusercontent.com`, а его клиент модели при недоступном прокси уходит на прямой выход. Одобренный исполняемый файл Codex получает переменные прокси явно (`codex-env-v1`: дочерние процессы Codex их не наследуют). Служба веб-инструмента платформы, если её развернут, получает свой профиль и слушатель (пункт 12). Учётка самого прокси — **ограничена прокси**: её выход широк по необходимости и ограничен обслуживаемыми политиками. Кроме того, её строка в ядре запрещает диапазоны `dial-guard/1` (пункт 11) как второй рубеж: перечисленные диапазоны, три префикса целиком и запрещённые диапазоны IPv4 в формах NAT64 и 6to4. Диапазон, который фильтр пакетов хоста выразить не может, записывается в отчёт квалификации, и второй рубеж заявляется только для того, что фильтр действительно применяет (строка P7).
8. **Разрешение имён правила по UID не покрывают.** На macOS запрос уходит с хоста от root-демона `mDNSResponder`, на Linux — от `systemd-resolved` при `nss-resolve`, поэтому правило пакетов по UID не доказывает ничего про DNS. Клиенту за прокси с CONNECT локальное разрешение не нужно, имена разрешает прокси; учётки, которым имена не нужны вовсе, получают песочницу, запрещающую резолвер. Агентам за своим слушателем и рабочим местам (пункт 10) имена не нужны. Пути DNS, Mach/XPC и резолвера — строки квалификации.
9. **Срок.** Всё это входит вместе с принудительной сетью (срез 2 платформы). До тех пор платформа записывает выбранный профиль как **заявленный**, и никакая кооперативная проверка не считается изоляцией. Рабочее место или любой другой недоверенный класс не включается до принудительной сети (контракт платформы §7.6), поэтому никогда не работает под заявленным или кооперативным профилем. Кооперативные профили — только для машин оператора без платформы.
10. **Рабочие места: ноль выхода (оператор, 13.10.2026).** Вызовы модели удалённого работника идут в его собственном агентском цикле на стороне донора. Поэтому у учётки `workplace` на нашем хосте нет привязки, слушателя и адреса прокси. Её строка запрещает весь выход, включая loopback TCP и UDP по IPv4 и IPv6, а политика привязки отклоняет любой профиль для этого класса. Два канала лежат вне правил по UID и закрываются отдельно:
    - разрешение имён — его запрещает песочница задачи у лаунчера (пункт 8);
    - Unix-сокеты: ни одна служба с выходом в сеть не допускает принципала рабочего места — ни брокер, ни управляющий сокет прокси, ни служба веб-инструмента.

    Входящий SSH — не выход рабочего места. pf и nftables относят принятое соединение к слушающему `sshd`, а вход не разрешает никакой переадресации (CIP-0009).
11. **Обслуживаемая политика.** Одни и те же правила обслуживают прокси провайдера модели и выход раннеров за зависимостями (N16).
    - **Разрешённые записи** — пары `host:port`; порт не подразумевается. Перед сравнением имена приводятся к канонической форме: нижний регистр, punycode, без точки в конце. IP-литералы отклоняются. Шаблон совпадает только целыми метками: `*.example.com` совпадает с `a.example.com`, но никогда с `example.com.evil.test` или `badexample.com`.
    - **Запрещённые порты.** Ни один профиль не может содержать почтовый порт (25, 110, 143, 465, 587, 993, 995, 2525) или порт резолвера (53, 853). Валидатор отклоняет такой профиль, а прокси — такое соединение.
    - **Защита адресов при соединении (dial guard)** `dial-guard/1` (*предложено*), не настраивается. Прокси сам разрешает имя и отказывает, если **хоть один** ответ попадает в запрещённый диапазон:
      - IPv4: `0.0.0.0/8`, `10.0.0.0/8`, `100.64.0.0/10` (общее адресное пространство, в нём tailnet), `127.0.0.0/8`, `169.254.0.0/16` (link-local, в нём адрес облачных метаданных), `172.16.0.0/12`, `192.0.0.0/24`, `192.168.0.0/16`, `198.18.0.0/15`, `224.0.0.0/4` и `240.0.0.0/4`;
      - IPv6: `::`, `::1`, `fc00::/7`, `fe80::/10` и `ff00::/8`;
      - префиксы целиком, какой бы адрес в них ни был вложен: IPv4-compatible `::/96`, локальный NAT64 `64:ff9b:1::/48` и Teredo `2001::/32`.

      Адреса IPv4-mapped, NAT64 (`64:ff9b::/96`) и 6to4 (`2002::/16`) разворачиваются, и проверяется вложенный адрес IPv4. Прокси соединяется с проверенным адресом и перепроверяет фактического собеседника, так что повторный запрос имени не может подменить адрес.

      Это перечень remote-workplace v2.1 (протокол §7), скопированный точно. Им пользуются и N15, и N16, а обслуживаемая политика называет его версию (пункт 5). Любое изменение, шире или уже, — новая версия; пересказ прозой список не заменяет.
    - **Квоты на личность**: запросы в минуту, одновременные соединения, байты в сутки, время жизни туннеля и тайм-аут простоя. Предел времени жизни задаётся в профиле и превышает самый длинный поток модели для квалифицированного кортежа. Любая превышенная квота отклоняется с одним и тем же статусом.
    - **Непрерывность суточного объёма.** Суточный объём принадлежит личности, а не слушателю и не процессу службы. Здесь личность — привязанное поколение учётки, в N16 — задача. Сутки — календарные сутки UTC, а не скользящие 24 часа.
      - Перезапуск, падение, перезагрузка политики, переприменение или новый слушатель для той же личности сохраняют уже израсходованное. Прежде чем снова пропускать трафик личности, прокси восстанавливает израсходованное или заранее зарезервированный объём. Пока остаток неизвестен, прокси отказывает.
      - Новый объём начинают только новое поколение учётки или новая задача. Новый слушатель или новое поколение службы для той же личности — нет.
      - Сутки сменяются по правилу времени платформы (F-21, R-TIME): шаг часов от недоверенного источника новых суток не начинает.
      - Обслуживаемая политика указывает, сколько можно потерять или перерасходовать при падении, например одну зарезервированную порцию.
    - **Поведение.** Профили агентов допускают только `CONNECT`. Перехвата TLS нет. Сбой ведёт к отказу, и ничто не уходит другим маршрутом (N10).
    - **Что гарантирует `CONNECT`.** Прокси гарантирует допущенный адресат (`host:port`) и адрес, который он проверил и с которым соединился. Внутрь туннеля он не смотрит, поэтому не знает, какое приложение там отвечает. Отсюда два остатка — те же, что remote-workplace v2.1 указывает для своих общих режимов (протокол §5):
      - через разрешённый адресат можно вынести данные;
      - общий фронт может отдать за разрешённым именем другой сайт (domain fronting).

      Перехват ради их закрытия не добавляется. Граница сильнее, чем адресат и адрес, требует отдельного проверенного дизайна, а где нужно — решения владельца. Прежде чем какой-либо текст заявит больше для квалифицированного кортежа, для этого кортежа нужны явные доказательства: как его общие фронты маршрутизируют TLS и приложения и что меняет перестройка топологии провайдера. Успешный обычный вызов провайдера таким доказательством не является.
    - **Журнал** — строки JSON: время, личность, поколение учётки, `profile_ref`, отпечаток обслуживаемой политики, хост, порт, разрешённый адрес, решение, код отказа, байты в каждую сторону и длительность. Никогда — тела, заголовки, токены, пути URL и запросы (N11).
12. **Доверенные локальные агенты и доступ к вебу (оператор, 13.10.2026).** Профиль доверенного локального агента пропускает `CONNECT` только к эндпоинтам провайдера модели для его квалифицированного кортежа. Это гарантия про адресат и адрес, а не про приложение внутри туннеля (пункт 11). Эндпоинты берутся из проверочных строк, никогда из документации. Для `codex-cli` 0.159.0 с входом через ChatGPT строки раунда 3 наблюдали такие хосты, все на порту 443 ([проверка агентских сред](../docs/harness-verification.md#results-round-3-2026-10-12-codex-login-and-refresh-r8r10)):
    - ход: `chatgpt.com` и `ab.chatgpt.com`;
    - первый ход в свежем домашнем каталоге: ещё региональные хосты `*.oaiusercontent.com`;
    - обновление токена: `auth.openai.com`.

    Включать ли адрес обновления, решает единственный владелец входа (CIP-0011). Если обновлением владеет брокер, профиль агента его не содержит, и с просроченным токеном агент получает отказ, а не обновляется сам. Агенты не собирают и не тестируют, поэтому ни один профиль агента не содержит реестра пакетов.

    **Доступ к вебу по умолчанию выключен** для всех агентов (оператор, позже той же ночью 13.10.2026), и дизайн работает без него:
    - задача несёт нужные ей ресурсы, например свежую документацию, только для чтения и по отпечатку;
    - доверенная сторона по запросу добирает остальное;
    - цикл донора ходит только к эндпоинтам своего провайдера и к нам, а у нас интернета нет;
    - клиентский инструмент загрузки в агентской среде, который сам скачивает URL, получает отказ для любого адресата вне профиля агента. Сайт, который отвечает за собственным общим фронтом провайдера, прокси не видит (пункт 11).

    **Поиск** можно включить только для личностей доверенного круга. Оператор включает его для каждой личности отдельно и никогда — для недоверенного класса. Возможны три формы:
    - **Поиск на стороне провайдера.** Он уходит через эндпоинт модели, поэтому сетевые правила его не видят. План запуска держит его выключенным, если у личности нет такого допуска.
    - **MCP-сервер на стороне донора** с собственным ключом донора (контракт платформы §7.2).
    - **Служба веб-инструмента платформы**, если её развернут. Она:
      - держит свой ключ в собственной служебной учётке;
      - обслуживает только порты 80 и 443 по пункту 11;
      - доступна агенту с допуском через Unix-сокет с проверкой UID собеседника и грантом, никогда через TCP.

      Служба видит запросы открытым текстом, поэтому её журнал — точка аудита.

### N16 Проверочные раннеры: выход за зависимостями вне хоста платформы (*предложено*, 13.10.2026)

Действует для эфемерных раннеров проверочной фазы доски на машине, отличной от хоста платформы. Оператор решил 13.10.2026, что агенты не собирают и не тестируют: подконтрольная проверочная фаза гоняет сборки и тесты в изолированных эфемерных раннерах на другой машине, без секретов. Раннеры, импорт кандидата и проверочная фаза — зона доски; её спецификация для них ещё не опубликована. Этот раздел задаёт только их сетевую сторону, чтобы та спецификация на него ссылалась.

1. **Два шага.** Шаг выборки разрешает зависимости по lock-файлам кандидата с выключенными install-скриптами и хуками сборки и не запускает кода кандидата. Затем шаг сборки и тестов идёт вовсе без сети: никаких интерфейсов, кроме loopback, и без резолвера. Зависимость, которую не принёс шаг выборки, ломает сборку; во время тестов ничего не скачивается.
2. **Один маршрут.** Единственный выход шага выборки — сокет задачи к службе выхода. Служба обслуживает для этой задачи политику из пункта 11 N15: разрешённые записи, запрещённые порты, защиту адресов (`dial-guard/1`), квоты и журнал. Личность задачи — её собственный слушатель. Шаг сборки и тестов сокета не получает.
3. **Зеркальные обработчики вместо туннелей.** Где у экосистемы есть обработчик с ограничением методов, шаг выборки использует его, а не `CONNECT`. Такой обработчик обслуживает GET и HEAD по грамматике путей и сверяет путь модуля с масками задачи; так делает обработчик `modules` в remote-workplace v2.1 для Go. Туннель `CONNECT` к реестру непрозрачен и одинаково легко несёт и загрузку, и скачивание. Где туннель — единственный вариант, гарантия покрывает допущенный адресат и проверенный адрес (пункт 11 N15), но не то, что уходит, и не то, какой сайт отвечает за общим фронтом. Модуль без маски — тоже канал наружу: прокси модулей обращается к тому источнику, который назван в запрошенном пути.
4. **Наших учётных данных** на раннере нет. Значит, загрузка в реестр может использовать только учётные данные, которые несёт сам кандидат; пункт 3 сужает этот остаток, но не убирает его.
5. **Результаты как данные.** Журнал шага выборки (строки JSON из пункта 11 N15) возвращается вместе с результатом проверки и привязан к отпечатку кандидата.
6. **Кандидат в реализацию.** Служба выхода remote-workplace v2.1 (`rwp-egress`) уже устроена так на Linux:
   - вызовы без сетевого интерфейса;
   - Unix-сокет на каждого работника;
   - обработчик `modules`, защита адресов, квоты и журнал;
   - отказ при любом сбое.

   Для обоих применений её счётчики должны переживать процесс службы (пункт 11 N15, непрерывность суточного объёма). В v2.1 они живут только пока жив процесс, так что перезапуск выдал бы новую суточную норму.

   Чтобы служить прокси провайдера модели на хосте платформы, ей понадобится ещё:
   - нативное развёртывание под служебной учёткой прокси;
   - слушатели TCP на loopback для каждой учётки, потому что агентские среды говорят с `HTTP_PROXY` по TCP;
   - статус обслуживаемой политики, который проверяет применение файрвола;
   - упаковка для macOS.

| Этап | Что даёт | Ценность |
| --- | --- | --- |
| A. Общий механизм | схема и файл профилей, резолвер, `EnvPatch`, бэкенд внешнего HTTP-прокси и провайдер Curator `curator-network`: `curator network exec <name> -- <cmd>`, `check [--probe]`, `list`, `show`, `add`, `remove`, `confirm` (заменяют предложенные `netrun --profile X -- <cmd>` и `netrun doctor X`) | независимые ручные запуски без глобального `export` |
| B. Лаунчер | `curator run --network`, проверенные точки входа, манифесты | окружение и сеть в одном запуске |
| C1. Оркестрация, явный профиль | `internal/spawn` в task-board и tb-sessiond на каждом реальном пути создания процессов (запуск, повтор, возобновление, рекурсивные дети) с явным `--network`, метаданные запуска | оркестратор запускает локальных субагентов через разные выходы в сеть |
| C2. Оркестрация, значения по умолчанию | значения по умолчанию из `runtimes.toml` для каждой привязки, значение по умолчанию проекта, их происхождение `origin` | значения по умолчанию без флага на каждом запуске |
| D. Управляемый шлюз | необязательный бэкенд sing-box, аренды во владении среды выполнения, поколения | автоматическое развёртывание прокси и WireGuard |
| Отдельный эпик | принудительная песочница исполнения | защита от обхода и изоляция |

A не ждёт D; C не ждёт ни удалённого пула, ни собственной агентской среды, ни распределённого журнала. C1 ждёт фазу 0 LP только там, где tb-sessiond сам собирает свои планы (патч должен попасть в этого сборщика); C2 ждёт фазу 1 LP (появление каталога). Приложение с контрактом из §5 входит в результаты этапа A.

Приёмка:

| Проверка | Ожидание |
| --- | --- |
| Параллельность | два процесса одной агентской среды одновременно используют два выхода в сеть, не трогая ни родителя, ни соседей |
| Композиция | конфликты нижнего и верхнего регистра и унаследованный `NO_PROXY=*` никогда не перекрывают явный профиль |
| Совместимость | настоящий HTTPS, стриминг, используемый websocket и подключения к локальным сервисам проверены для каждой точки входа на закреплённых версиях |
| Отказ | неизвестный, запрещённый, недоступный или неподдерживаемый профиль приводит к отказу до запуска; скрытого перехода на прямое соединение нет |
| Оркестрация | привязка применяется в самом дочернем процессе, включая заявленные пути повтора и возобновления |
| Учётные данные | модуль не меняет учётную запись и не пропускает ни одного секрета в конфигурацию, манифесты или логи |
| Совместимость с существующими запусками | запуски без выбора ведут себя как раньше; допуск и терминальный жизненный цикл не обходятся |
| Честный уровень гарантии | публикуется `assurance = cooperative`; запрос `enforced` не может получить кооперативный запуск |
| Движки | эндпоинты движков на loopback есть в списке обхода каждого профиля |
| `unset` на границе | конфликтующей переменной прокси, которая есть только на хосте, создающем ребёнка, в окружении ребёнка нет |
| Равенство привязок | повторное подключение или возобновление существующего запуска, у которого под тем же именем изменилось содержимое профиля, отклоняется с `network_profile_drift` и никогда не перемаршрутизируется на уровне сессии; новое назначение на работающий хост с другой привязкой даёт `network_scope_unsupported`, если адаптер не умеет маршрут на уровне сессии |

## 4. Правила и не-цели

- Никогда `os.Setenv`, никогда смена системного прокси, никогда переписывание общей конфигурации; патч живёт в окружении дочернего процесса.
- Никогда сырой адрес прокси от оркестратора; только идентификаторы профилей из разрешённого набора.
- Никогда скрытый переход на прямое соединение, на другой VPN или на другую учётную запись.
- Никогда переменные прокси как `env_names`; это собственные литералы.
- Это не LLM-шлюз, не песочница, не оркестратор VPN и не второй супервизор процессов.

## 5. Приложение с контрактом (результат этапа A)

Короткое приложение с тестовыми векторами, написанное вместе с кодом, фиксирует то, что этот документ только называет:

| Область | Что определяет |
| --- | --- |
| Дайджест профиля | нормализованное содержимое (N3), канонический JSON с отсортированными ключами и явной версией схемы, SHA-256 по этим байтам |
| `EnvPatch` | точный набор `unset` и набор `set` для каждого адаптера, оба написания, `ALL_PROXY` и переменные websocket только там, где проверены |
| Равенство привязок | список членов (N3) и то, что исключено: время пробы, аренда, поколение |
| Векторы | конфликты регистра, унаследованный `NO_PROXY=*`, конфликтующая переменная только на хосте, изменённое содержимое под неизменным именем, движок на loopback в списке обхода и вне его |
